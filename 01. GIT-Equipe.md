# 🚀 Exercício — Desenvolvimento Java em Equipe com Git e GitHub

Neste exercício, a equipe desenvolverá um pequeno sistema Java utilizando **Orientação a Objetos, Herança, Sobrescrita e Polimorfismo**.

O tema poderá ser escolhido pela equipe entre as opções apresentadas neste enunciado.

Independentemente do tema escolhido, **todas as equipes deverão seguir exatamente as mesmas regras técnicas e o mesmo fluxo de trabalho com Git e GitHub**.

> 👥 O trabalho deverá ser realizado em **trios**.

---

# 🎯 Objetivos de Aprendizagem

Ao final da atividade, a equipe deverá ser capaz de:

* modelar uma hierarquia de classes utilizando herança;
* utilizar atributos e métodos em uma superclasse;
* criar subclasses especializadas;
* sobrescrever métodos utilizando `@Override`;
* aplicar polimorfismo;
* criar e trabalhar com branches;
* realizar commits;
* enviar branches para o GitHub;
* abrir Pull Requests;
* realizar Code Review;
* integrar alterações desenvolvidas por diferentes integrantes;
* atualizar uma branch utilizando `rebase`;
* identificar e resolver conflitos;
* compreender o fluxo de desenvolvimento colaborativo.

---

# 👥 Organização da equipe

A equipe será formada por **3 integrantes**.

Cada integrante deverá ser responsável por uma parte do desenvolvimento.

| Integrante | Responsabilidade principal                 |
| ---------- | ------------------------------------------ |
| Pessoa A   | Superclasse + estrutura inicial do projeto |
| Pessoa B   | Primeira subclasse                         |
| Pessoa C   | Segunda subclasse                          |

⚠️ **Cada integrante deverá realizar seus próprios commits utilizando sua conta do GitHub.**

Não será considerado trabalho em equipe um projeto no qual apenas uma pessoa realizou todos os commits.

# 🧱 1. Superclasse

A superclasse deverá possuir obrigatoriamente:

* pelo menos **2 atributos privados**;
* construtor;
* getters e setters;
* método `toString()`;
* pelo menos **1 método que será sobrescrito pelas subclasses**.

Exemplo conceitual:

```java
public class Superclasse {

    private String nome;
    private int codigo;

    public Superclasse(String nome, int codigo) {
        this.nome = nome;
        this.codigo = codigo;
    }

    public void executarAcao() {
        System.out.println("Executando ação genérica");
    }

}
```

⚠️ Este código é apenas um exemplo de estrutura.

A equipe deverá adaptá-lo ao tema escolhido.

---

# 🧩 2. Primeira subclasse

A primeira subclasse deverá:

* utilizar `extends`;
* possuir pelo menos **1 atributo próprio**;
* possuir construtor;
* possuir getter e setter do atributo próprio;
* sobrescrever pelo menos **1 método da superclasse**;
* utilizar a anotação `@Override`.

Estrutura esperada:

```java
public class SubclasseA extends Superclasse {

    private String atributoEspecifico;

    @Override
    public void executarAcao() {
        // comportamento específico
    }

}
```

---

# 🧩 3. Segunda subclasse

A segunda subclasse deverá seguir as mesmas regras:

* utilizar `extends`;

* sobrescrever pelo menos **1 método da superclasse**;
* utilizar `@Override`.

---

# 🔄 4. Polimorfismo

O projeto deverá obrigatoriamente demonstrar polimorfismo.

No `Main.java`, os objetos das subclasses deverão ser armazenados utilizando o tipo da superclasse.

Exemplo:

```java
List<Superclasse> objetos = new ArrayList<>();

objetos.add(new SubclasseA(...));
objetos.add(new SubclasseB(...));
```

Depois, utilize uma estrutura de repetição:

```java
for (Superclasse objeto : objetos) {
    objeto.executarAcao();
}
```

O comportamento executado deverá mudar de acordo com o objeto armazenado.

---

# ▶️ 5. Main.java

O `Main.java` deverá demonstrar claramente o funcionamento do sistema.

Deverá existir:

* pelo menos **1 objeto da primeira subclasse**;
* pelo menos **1 objeto da segunda subclasse**;
* uma coleção utilizando o tipo da superclasse;
* chamada de métodos herdados;
* chamada de métodos sobrescritos;

* informações exibidas de maneira clara no console.

# 🌳 Organização das branches

O projeto deverá possuir:

```text
main
 │
 └── dev
      │
      ├── feature/superclasse
      │
      ├── feature/subclasse-a
      │
      └── feature/subclasse-b
```

### `main`

Representa a versão final e estável do projeto.

### `dev`

Será utilizada para integrar o trabalho da equipe.

### `feature/...`

Cada integrante deverá trabalhar em sua própria branch.

# 🔄 Atualizar a branch antes do Pull Request

```bash

```

Caso exista conflito, ele deverá ser resolvido.

# ⚔️ Conflito esperado no README

É possível que apareça algo semelhante a:

```text

Integrantes que contribuíram nesta versão: [Pessoa A]
=======
Integrantes que contribuíram nesta versão: [Pessoa B]
>>>>>>> commit
```

A equipe deverá manter as duas contribuições:

```text

```

```bash

git rebase --continue
```

Verificar:

```bash
git status
```

# 🔀 Pull Request final

Quando todo o projeto estiver funcionando corretamente:

```text
dev → main
```

Deverá ser aberto um último Pull Request.

Antes do merge, verificar:

* código compilando;
* programa executando;
* herança funcionando;
* `@Override` presente;
* polimorfismo demonstrado;
* README completo;
* integrantes identificados;
* branches individuais utilizadas;
* Pull Requests realizados;
* revisões realizadas.

Somente depois disso deverá ocorrer o merge para a `main`.
